# aha · 架构总纲 v2 —— 两端一坐标系

> 本文**承接并升级** [`ARCHITECTURE.md` (v1)](./ARCHITECTURE.md)。
> v1 的三层解耦、Content API / Match API 两道契约、schema 与信号模型**全部保留有效**。
> v2 只做一件事:**把"人"从大脑里的一个变量,升格为与"画"对称的一端**;并据此应对两个新约束——**几万+数据**与**多终端**。

---

## 0. 相对 v1 改了什么

| | v1 | v2(本文) |
|---|---|---|
| 人的地位 | L3 大脑里的 `TasteProfile`(一个变量) | **一等公民:与"画"对称的一端**(会生长的点云) |
| 统一模型 | 三层 + 两道 API | **两端 + 一坐标系 + 可换终端** |
| 数据规模 | 浏览器内 JSON | **几万+ → 数据服务 + 向量索引** |
| 终端 | Web(+小程序) | **任意终端,皆为客户端**;Web 只是第 1 个 |
| 匹配本质 | "聪明的匹配引擎" | **同一坐标系里算最近邻**(画落点 ⟷ 人落点) |

> 一句话:v1 讲"三层怎么解耦",v2 讲"**为什么画和人是同一种东西的两半**"。

---

## 1. 核心论断

> **画与人,是同一坐标系里的两团点云。交互(任何终端)只做三件事:把人投影上去、取最近的画、把这次接触沉淀回人。**

- **画端**(第一部分):人类既有艺术,结构化成**不可变规律 + 可追加数据**的资产。
- **人端**(第三部分):每个用户,沉淀成一团**会生长**的审美点云。
- **交互**(第二部分):居中的连接机制,**与终端无关**——网页是第一层皮,不是唯一。

两端能相连,根本原因只有一个:**它们说同一种坐标语言**。

---

## 2. 三段拓扑

```
        ┌──────────── 同一套坐标系 = 唯一的契约 ────────────┐
        │                                                    │
 ┌──────┴───────┐      ┌──────────────────┐      ┌──────────┴────────┐
 │  画端 · 数据  │      │  交互 · 多客户端  │      │  人端 · 审美档案   │
 │  几万+节点    │ ◀──▶ │  web(现20页玩法) │ ◀──▶ │  身份绑定          │
 │  向量检索 API │      │  未来: App/装置/  │      │  会生长的点云      │
 │  不可变+可追加│      │       语音/AR     │      │  重心·离散·轨迹·漂移│
 │ (第一部分/L1) │      │  每个终端=一层皮  │      │  (第三部分)        │
 └──────────────┘      │ (第二部分/L2)     │      └───────────────────┘
                       └──────────────────┘
                        投影人 → 取画 → 回吐信号
```

**对称性**:画端是"**产出**"在坐标里的点云;人端是"**偏好**"在坐标里的点云。
二者同坐标系,所以匹配 = 在同一空间里算距离。人端的数据模型,直接**镜像艺术家点云**(对标 `kg-artist`:重心 / 离散 / 轨迹)。

---

## 3. 命门:一套坐标系

整套系统只靠**一组共享坐标轴**对话,源自世界 B 那条生成因果链派生的向量:

```
再现 ↔ 表现   ⊥   结构 ↔ 感知   ⊥   秩序 ↔ 张力   ⊥   节制 ↔ 强度   (+ 世界观区 / 题材 / 情绪锚点 …)
```

- **画**:每幅画/每个风格 = 这组轴上的一个落点(已在 `kg-style-vectors` / `kg-worldview` 落地)。
- **人**:`kg-taste` 已经在把用户投影到 `(再现-表现 ⊥ 结构-感知)` 并给出「你在这里」——**这就是人端的种子**。
- **匹配**:`nextFor` / `rank` / `matchByMood` 全部退化成"在这组坐标里找最近邻 + 反茧房探索位"。

> 坐标系是契约本身。换终端、加数据、升算法,都不动这组轴的语义;只动语义就发大版本。

---

## 4. 画端(第一部分)· 不可变资产 + 可追加

= v1 的 **L1 内容层**,职责不变;v2 的新增量是**规模**。

- **不可变** = 坐标轴与 schema 结构恒定(规律);**可追加** = 节点(画/艺术家/风格)只增。
- **几万+ 的后果**:浏览器内整包 JSON **作废**。画端毕业为**数据服务**:
  - 服务端存储 + **向量索引**(按坐标算 KNN,是匹配的物理基础)
  - 按需分页 / 过滤 / 邻居查询(沿用 v1 Content API 的 `list / neighbors / byColor / byMood / search`)
  - 离线管线继续算 embedding / 主色 / 建边,产出灌入服务
- **坐标向量**来自世界 B 的因果链:世界观 → 题材 → 语言 → 感知 → 画外音 → 风格(末端涌现)。

---

## 5. 人端(第三部分)· 会生长的审美档案 【v2 新增的核心】

这是 v1 缺的一块。把 v1 藏在 L3 里的 `TasteProfile`,**抽出来、加身份、做成持久实体**。

**为什么必须服务端 + 身份绑定:**
- 你选了"**会生长 + 是资产**"。`localStorage` = 锁死在一台浏览器,逛完就散——既跨不了终端,也谈不上资产。
- 多终端要"档案跟着人走",唯一办法是:**人端搬到服务端,挂在一个身份(账号/标识)后面**。这是方案 1 的硬门槛,不是优化项。

**数据模型(镜像艺术家点云):**
```
Person = {
  id,                          // 身份(账号 / 匿名稳定标识 / 跨端可迁移)
  centroid: number[],          // 重心:你的审美在坐标系里的质心
  spread:   number,            // 离散:你口味的宽窄(专一 ↔ 杂食)
  trajectory: Point[],         // 轨迹:质心随时间的移动路径(可回放)
  drift:    vector,            // 漂移:你最近在往哪个方向走
  exploreAppetite: 0..1,       // 反茧房探索胃口
  topRegions / topThemes,      // 派生的可读标签:你常驻哪些世界观区 / 母题
  events:   Signal[]           // append-only 事件流(画像由它派生,可重算)
}
```

**生长方式**:`append-only 事件流 → 派生当前画像`。
每次交互(看/停留/心动/推门/二选一…)是一条事件,**只追加不覆盖**;`centroid / drift / trajectory` 都从事件流派生,因此**可重算、可回放、可解释"你怎么变成现在这样"**。

> 人端长出来后,`kg-artist`(艺术家点云)与 Person(用户点云)是**同一套渲染**的两侧——产出侧 vs 消费侧。

---

## 6. 交互层(第二部分)· 可换终端

= v1 的 **L2 体验层**,职责不变;v2 把"客户端"从"Web + 小程序"泛化为"**任意终端**"。

- **Web = 客户端 #1**(现有 ~20 页玩法:漂流/星空/吸色/对话/情绪盘…)。
- **未来终端**:App / 实体装置 / 语音 / AR —— 每个都只是一层"皮"。
- **每个终端只认坐标契约**,做三件事:① 把人投影到坐标系 ② 取最近的画 ③ 把这次接触回吐成事件。
- 每种玩法同时是一台**偏好传感器**(二选一=强信号、吸色=色彩信号、停留=兴趣强度),选主力玩法既看体验、也看它喂给人端的信号干不干净。

---

## 7. 数据流:投影 → 匹配 → 沉淀(闭环)

```
[任意终端] 用户来 → 读 Person.centroid(在坐标系里定位"你在这里")
        → 在画端向量索引里取最近邻 + 探索位 → 渲染
        → 用户操作 → 生成 Signal 事件 → append 到 Person.events
        → centroid / drift / trajectory 派生更新
        → 下一次投影立刻更准(越逛越准 · 且跨终端连续)
```

与 v1 数据流一致,差别在:**画像不再活在浏览器,而在服务端的 Person 里;闭环跨终端连续。**

---

## 8. 从现状到目标(演进三步)

**现状(单终端 demo):** 画 = 静态 `data/*.json`(`fetch` 整包) · 人 = `localStorage`(`taste` / `aha_mystar`)。
两端都困在浏览器里——这是 demo 架构,撑不住几万数据,也跨不了终端。

1. **立人端**:把 `localStorage` 画像 → 服务端 `Person` 实体(身份 + 事件流 + 派生画像)。**先解多终端的命门。**
2. **扩画端**:静态 JSON → 数据服务 + 向量索引,迁到几万+ 规模;Content API 端点化。
3. **泛终端**:Web 抽成"客户端 #1",其余玩法插件化;新终端按同一坐标契约接入。

> 顺序可调,但**第 1 步(人端服务端化)是方案 1 成立的前提**,建议优先。

---

## 9. 与 v1 的关系(保留 / 变化)

- **保留**:三层解耦思想、Content API / Match API 两道契约、五层 schema、信号模型、L2 插件契约、"护城河集中在数据 × 懂你"。
- **变化**:① `TasteProfile` 升格为一等实体 `Person`(身份 + 持久 + 会生长);② "坐标系"显式化为唯一契约;③ 规模拉到几万+ 触发"JSON → 向量服务";④ "客户端"从 Web/小程序泛化为任意终端。
- **一句话**:v1 是"**三层怎么搭**",v2 是"**画与人是同一坐标系里对称的两端,终端只是皮**"。
